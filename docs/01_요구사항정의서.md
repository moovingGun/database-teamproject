## 1. 시스템 개요

| 항목 | 내용 |
|---|---|
| 시스템명 | SI-PMS (SI Project & People Management System) |
| 목적 | SI 업체의 **프로젝트 – 투입 인력 – 직무 – 기간** 을 체계적으로 관리하고, 프로젝트 종료 시 **고객/PM/동료 평가** 를 수집하여 경력관리·인사고과·인센티브 산정의 기초자료를 제공 |
| 대상 조직 | 직원 100명 (개발자 70명, 마케팅·경영관리·연구개발 30명), 월평균 10개 프로젝트 수행 |
| 형태 | 사내 업무용 웹 시스템 (Flask) + 관계형 DBMS (MySQL 8.0) |
| 범위 | 회원가입/로그인, 직원·기술 관리, 발주처·프로젝트 관리, 투입 관리, 평가(3종), 경영진 조회/리포트, 데이터 적재 스크립트 |

## 2. 업무 현황 및 용어

| 용어 | 정의 |
|---|---|
| 직원 | 회사 구성원. **개발자**(프로젝트 투입 대상)와 **지원직**(마케팅/경영관리/연구개발)으로 구분 |
| 기술등급 | 개발자의 등급: 초급 / 중급 / 고급 / 특급 (경력 기준 산정, 경영진 심사로 확정) |
| 직무 | 프로젝트에서 수행하는 역할: PM, PL, 분석자, 설계자, 프로그래머, 테스터 |
| 투입 | 개발자가 특정 프로젝트에 특정 직무·기간·투입률로 참여하는 것. 프로젝트 전체 기간 또는 일부 기간 |
| 발주처 | 프로젝트를 발주한 고객사. 담당자는 고객 평가의 평가자 |
| 프로젝트 평가 | 프로젝트 종료 시점에 수행하는 **고객 평가 / PM 평가 / 동료 평가**. 평가 항목은 업무수행·커뮤니케이션 능력, 항목별 평점과 평가 내용 |
| 경영진 | 타 직원 정보를 검색·조회하고 투입/프로젝트를 관리할 권한을 가진 사용자 |

## 3. 사용자(액터) 및 권한

| 액터 | 설명 | 주요 권한 |
|---|---|---|
| 일반직원 (개발자) | 프로젝트에 투입되는 개발자 | 회원가입, 본인 정보/보유기술 관리, 본인 투입·경력·평가결과 조회, 동료 평가 입력 |
| 일반직원 (지원직) | 마케팅/경영관리/연구개발 | 회원가입, 본인 정보 관리, 프로젝트 목록 조회 |
| PM (역할) | 프로젝트에 PM 직무로 투입된 개발자 | + 팀원 PM 평가, 고객 평가 의뢰·결과 보고 |
| 경영진 | `auth_role = EXECUTIVE` 계정 | + 전 직원 검색·상세 조회, 프로젝트 등록/상태 변경, 투입 등록/철수, 기술등급 변경, 시점별 현황·평가 결과·인센티브 리포트 |
| 발주처 담당자 (외부) | 고객사 담당자 | 로그인 없이 토큰 링크로 고객 평가서 작성 |

## 4. 기능 요구사항

### 4.1 회원가입 · 인증

| ID | 요구사항 | 출처 |
|---|---|---|
| FR-01 | 직원은 회원가입 페이지에서 본인 정보(이름, 주민등록번호, 최종학력, 입사일, 직원 구분, 개발자인 경우 기술등급·경력 기산일)를 입력하여 DB 에 저장한다 | PD ¶2 |
| FR-02 | 로그인 ID 는 **중복 체크** 기능을 제공한다. 이미 등록된 ID 로 가입 요청 시 **에러 메시지** 를 출력하고 중복되지 않는 새 ID 를 입력할 수 있어야 한다 (화면의 [중복확인] 버튼 + 서버 측 재검증 + DB UNIQUE 제약) | PD ¶2 |
| FR-03 | 사번은 **정해진 규칙에 따라 자동 부여** 한다: `E` + 입사연도 2자리 + 연도별 일련번호 4자리 (예: E260001). DB 트리거가 채번 | PD ¶2, 가정 A-1 |
| FR-04 | 가입한 직원은 로그인/로그아웃할 수 있으며 비밀번호는 해시(PBKDF2-SHA256)로 저장한다 | NFR |
| FR-05 | 직원은 본인 정보(이름, 학력, 연락처, 경력 기산일/부서, 비밀번호)를 **수정/변경** 할 수 있다. 기술등급은 본인이 변경할 수 없다 | PD ¶2, 가정 A-4 |

### 4.2 직원 · 기술(Skill Set) 관리

| ID | 요구사항 | 출처 |
|---|---|---|
| FR-06 | 직원 정보로 직원번호(사번), 직원명, 주민등록번호, 최종학력을 관리한다 | PD ¶2 |
| FR-07 | 직원은 **개발자 / 지원직** 서브타입으로 구분하며, 개발자는 기술등급·경력, 지원직은 부서(마케팅/경영관리/연구개발)·직책을 추가로 관리한다 | PD ¶1, 가이드라인 |
| FR-08 | 개발자는 **경력**(경력 기산일 → 총 경력 개월 수 산출)과 **경험한 기술(Skill Set)** 을 숙련도·사용 경력·최근 사용일과 함께 관리한다 | PD ¶2 |
| FR-09 | 경영진은 이름/사번, 직원 구분, 기술등급, 보유 기술, 특정 일자 가용 여부로 **타 직원을 검색** 하고 상세(경력 이력, 기술, 평가 종합, 등급 변경 이력)를 조회할 수 있다. 일반직원은 본인 정보만 조회 가능 | PD ¶3 |
| FR-10 | 경영진은 개발자의 기술등급을 변경할 수 있으며 변경 이력(변경 전/후, 처리자, 사유)이 자동 기록된다 | 가정 A-4 |

|---|---|---|
| FR-11 | 프로젝트는 프로젝트번호, 프로젝트명, 착수일자/종료일자, 발주처를 관리한다. 상태(예정/진행중/종료/취소), 계약금액, 개요, 요구 기술을 추가 관리 | PD ¶2 |
| FR-12 | **발주처는 별도 엔티티** 로 관리(발주처명, 사업자등록번호, 업종, 주소)하고 발주처별 담당자(이름, 직위, 이메일, 연락처)를 1:N 으로 관리한다 | 가이드라인 |
| FR-13 | 프로젝트번호는 규칙(`P` + 착수연도 + `-` + 일련번호 3자리, 예: P2026-001)에 따라 자동 부여한다 | 가정 A-2 |

|---|---|---|

| FR-18 | 경영진은 투입을 조기 종료(철수)할 수 있다 (종료일 변경, 이력 보존) | 가정 A-7 |

### 4.5 경영진 조회 (현황 · 이력)

| ID | 요구사항 | 출처 |
|---|---|---|

| FR-21 | 개인별 **경력관리**: 직원별 프로젝트 참여 이력(프로젝트, 발주처, 직무, 기간, 투입률)과 보유 기술, 총 경력을 조회한다 | PD ¶3 |
| FR-22 | **인센티브 지급 기초자료**: 연도별 종료 프로젝트의 평가 종합점수를 개인별로 집계하여 등급과 지급 권고액을 산출한다 | PD ¶3 |

### 4.6 프로젝트 평가

| ID | 요구사항 | 출처 |
|---|---|---|
| FR-23 | 프로젝트 **종료 시점** 에 평가를 시행한다. 평가 유형은 **고객 평가 / PM 평가 / 동료 평가** 이며 평가 정보는 슈퍼타입-서브타입으로 관리한다 | PD ¶4, 가이드라인 |
| FR-24 | 각 평가에는 **평가자와 피평가자** 가 존재한다. 고객 평가의 평가자는 발주처 담당자, PM/동료 평가의 평가자는 개발자 | PD ¶4 |
| FR-25 | 평가 항목은 **업무수행 평가, 커뮤니케이션 능력 평가** 이며 각 항목당 **평점(1~5)과 평가 내용** 을 관리한다. 항목은 코드 테이블로 확장 가능 | PD ¶4 |
| FR-26 | **고객 평가**: 프로젝트 종료 시점에 **PM 이 주관** 하여 발주처 담당자에게 참여 직원 전원에 대한 평가서를 **의뢰** 하고, 담당자가 외부 링크로 제출하면 PM 이 결과를 **회사에 보고** 한다 (의뢰됨 → 제출 → 보고완료) | PD ¶4 |
| FR-27 | **동료 평가**: 프로젝트 참여자가 **자기 이외의** 참여자를 평가한다 (피평가자에게 익명 집계) | PD ¶4 |
| FR-28 | **PM 평가**: PM 이 프로젝트 팀원을 평가한다 (+ 인센티브 추천 여부) | PD ¶4 |
| FR-29 | 평가 결과는 인사고과·인사평가 근거자료로 활용되도록 피평가자별 고객/PM/동료 평균, 가중 종합점수, 인센티브 등급으로 집계한다 | PD ¶4 |

## 5. 가정사항 (Problem Description 에 없는 내용 — 설계에 반영)

| ID | 가정 | 반영 위치 |
|---|---|---|
| A-1 | 사번 규칙: `E` + 입사연도(YY) + 연도별 일련번호(4자리). 동시 가입 시에도 중복되지 않도록 행 잠금 기반 채번 | `trg_employee_bi`, `sp_next_seq`, `seq_counter` |
| A-2 | 프로젝트번호 규칙: `P` + 착수연도(YYYY) + `-` + 일련번호(3자리) | `trg_project_bi` |
| A-3 | 기술등급은 초급/중급/고급/특급 4단계. 총 경력 36/72/120개월을 기준으로 **권고 등급** 을 산출하고 최종 등급은 경영진이 확정 | `v_employee.recommended_grade`, FR-10 |
| A-4 | 기술등급 변경은 경영진만 가능하며 변경 이력을 보존(인사 근거) | `grade_history`, BR-15 |
| A-5 | 직무별 최소 기술등급: PM 고급↑, PL/분석자/설계자 중급↑, 프로그래머/테스터 초급↑ | `job_role.min_grade`, BR-07 |
| A-6 | 투입률(%) 개념 도입: 한 사람이 같은 기간에 여러 프로젝트에 부분 투입 가능하되 합계 100% 이하. 같은 기간 프로젝트 PM 은 1명 | BR-05, BR-06 |
| A-7 | 프로젝트 상태 흐름: 예정 → 진행중 → 종료 / 취소. 종료 처리 시 실제 종료일로 열린 투입을 정리. 종료·취소 프로젝트에는 신규 투입 불가 | FR-14, AR-01 |
| A-8 | 평가는 프로젝트 상태가 **종료(COMPLETED)** 일 때만 등록 가능. 피평가자·평가자는 해당 프로젝트 참여자여야 함 | BR-08, 09, 13, 14 |
| A-9 | 평점은 1~5점 정수. 항목 가중치(기본 1:1)로 평가 평균을 내고, 유형 가중치 고객 40% / PM 40% / 동료 20% 로 종합점수를 산출(없는 유형은 가중치 재배분). 등급 S≥4.5, A≥4.0, B≥3.0, C | `eval_item.weight`, `eval_type_weight`, `v_project_eval_summary` |
| A-10 | 인센티브 지급 권고액 = 연간 평균 종합점수 등급(S 150% / A 100% / B 50% / C 0%) × 기준액 100만원 × 참여 프로젝트 수 (정책 파라미터) | 리포트 S5 |
| A-11 | 고객 평가는 발주처 담당자가 사내 계정 없이 **토큰 링크** 로 입력. 의뢰 1건당 피평가자 1명이며 담당자는 한 화면에서 전원 입력 | `customer_eval.access_token` |

### 8.1 시나리오 A — 고객사 변경요청 및 승인 관리

프로젝트 진행 중 고객사가 기능 추가·변경을 요청하면 PM 이 접수하고, 영향 분석(검토안)을 작성해 경영진 승인과 고객 동의를 모두 받은 경우에만 프로젝트 계획(종료예정일·계약금액)에 반영한다. 반영 전후 값은 이력으로 남는다.

| ID | 요구사항 |
|---|---|
| FR-A1 | PM 은 자신이 PM 인 예정·진행 중 프로젝트에 대해 고객 담당자, 요청일, 제목, 내용, 사유로 변경요청을 접수한다. 요청번호(CR+연도-순번)는 자동 부여 |
| FR-A2 | PM 은 제안 종료예정일, 추가 계약금액, 검토 의견으로 검토안을 작성한다. 일정·금액 자동 산정은 하지 않는다 |
| FR-A3 | 경영진은 최신 검토안을 승인 또는 반려하고 결정일·사유를 남긴다 |
| FR-A4 | 내부 승인 후 PM 은 고객사의 동의 또는 거절을 동의 담당자, 확인일, 확인 근거와 함께 기록한다. 내부 승인만으로 고객 동의로 보지 않는다 |
| FR-A5 | 승인과 동의가 모두 끝난 검토안만 PM 또는 경영진이 계획에 반영한다. 종료예정일(계획)은 실제 종료일과 구분한다 |

### 8.2 시나리오 B — 프로젝트 평가 기반 역량 개선 및 교육 이수 관리

교육 담당자(경영관리 직원 중 지정)가 종료 프로젝트의 평가 내용과 보유 기술을 검토해 역량개선계획(직원 1명 × 추천 교육과정 1개)을 수립하고, 직원은 추천 과정의 개설 일정에 신청한다. 교육 종료 후 담당자가 수료 여부를 기록한다.

| ID | 요구사항 |
