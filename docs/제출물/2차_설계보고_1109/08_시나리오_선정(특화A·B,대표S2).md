# 시나리오 선정 — 무엇을 어떤 시나리오로 만들었는가

> 과제에는 두 종류의 "시나리오" 가 있다. 둘을 구분해서 어떤 것을 골랐고 어디까지 만들었는지 적는다.
> ① **조별 특화 비즈니스 로직(시나리오)** — 핵심 가이드라인 4: "기본 사내 업무 외에 추가 비즈니스 로직의 고도화·구체화를 설계에 반영" (11/09 설계 보고 각주 2)
> ② **데모 시나리오** — 핵심 가이드라인 5: "⌈조원 수/2⌉개(2개 이상 테이블 조인), 그중 대표 1개에 성능 향상 기법 적용·실험" (12/07 최종보고)

## 1. 조별 특화 시나리오 — A·B 둘 다 채택

팀원 두 명이 각각 제안한 시나리오를 둘 다 구현했다. 하나는 **프로젝트 계획 변경(계약·일정)**, 하나는 **평가 결과의 사후 활용(인재 육성)** 이라 겹치지 않고, 기본 업무(투입·평가)의 앞뒤를 메운다.

### A. 고객사 변경요청 및 승인 관리

| 항목 | 내용 |
|---|---|
| 왜 고도화인가 | Problem Description 은 프로젝트 착수·종료일만 관리한다. 실제 SI 에서는 고객사가 범위·일정 변경을 요청하고 승인 뒤 계약이 바뀌므로, **계획 변경의 이력과 승인 절차** 를 데이터로 남겨야 한다 |
| 업무 흐름 | PM 접수 → PM 검토안(영향 분석: 제안 종료예정일·추가 계약금액) → 경영진 승인/반려 → 고객사 동의/거절 기록 → 계획 반영(종료예정일·계약금액 변경, 전후 값 이력). 승인 후 내용이 바뀌면 **새 차수** 로 재검토 |
| 신규 엔터티 3개 | `change_request`(변경요청) ─< `change_review`(검토안, 차수) ─ `change_history`(적용이력 0..1). 프로젝트에 `end_date`(종료예정)와 `actual_end_date`(실제 종료) 분리 |
| 규칙 | BR-16 ~ BR-23 (트리거 7개 + `sp_apply_change`) |
| 화면 | 변경요청 접수·검토안·고객 동의·반영(PM), 승인 대기(경영진), 변경요청 처리 현황 리포트 |
| 데모 | **S7** — 10개 테이블 조인, 미처리 요청까지 포함 |
| 설계 결정 | 팀 초안 5개 엔터티 → 3개로 합침 (`07_핵심설계결정.md` D-11) |

### B. 프로젝트 평가 기반 역량 개선 및 교육 이수 관리

| 항목 | 내용 |
|---|---|
| 왜 고도화인가 | Problem Description 의 평가는 "인사고과 근거" 에서 끝난다. 평가 결과를 **직원 육성** 으로 연결하면 평가 데이터의 쓰임이 생긴다 |
| 업무 흐름 | 교육 담당자(경영관리 직원 중 지정)가 종료 프로젝트 평가·보유 기술을 검토 → 직원별 역량개선계획(추천 과정·개선 목표·이수 목표일) → 직원이 추천 과정의 교육일정에 신청/취소 → 교육 종료 후 수료/미수료 기록 → 평가 + 이수 현황 조회 |
| 신규 엔터티 4개 | `training_course`(교육과정) ─< `training_session`(교육일정), `development_plan`(역량개선계획 = 직원 × 추천 과정), `training_enrollment`(교육신청 = 계획 × 일정). 지원직에 `is_training_manager` |
| 규칙 | BR-24 ~ BR-29 (트리거 3개) |
| 화면 | 교육 관리·역량개선계획 수립(담당자), 내 교육(직원), 교육 이수 현황 리포트 |
| 데모 | **S8** — 9개 테이블 조인, 미신청 계획까지 포함 |
| 설계 결정 | 신청 테이블에서 직원번호 제거(계획에서 결정), 이수 상태는 이력에서 계산 (D-12) |

둘 다 11/09 제출 파일 `03-3_테이블정의서.xlsx` 의 '비즈니스 로직 고도화 방안' 시트, ERD `04_chg.png`·`05_edu.png`, CRUD 매트릭스(프로세스 25~35)에 들어가 있다.

## 2. 데모 시나리오 — 8개 준비, 대표는 S2

조원 3명이면 ⌈3/2⌉ = 2개가 요구이지만, 기본 업무의 핵심 조회 6개와 특화 시나리오 2개를 모두 데모로 준비했다. 전부 2개 이상 테이블 조인이며 웹 화면과 1:1 로 대응한다 (`05_데모시나리오.md`, SQL `db/demo/demo_scenarios.sql`).

| # | 시나리오 | 조인 | 화면 | 비고 |
|---|---|---|---|---|
| S1 | 경영진 대시보드 — 진행 중 프로젝트 수, 프로젝트별 투입 인원·PM·직무 | 5 | `/` | PD ¶3 "현재 몇 개의 프로젝트" |
| **S2 ★** | **과거 특정 시점에 누가 어느 프로젝트에 어떤 직무로** | 6 | `/reports/staffing` | **대표 시나리오** |
| S3 | 개인별 경력 — 참여 이력 + 보유 기술 + 총 경력 | 7+3 | `/employees/<id>` | PD ¶3 "개인별 경력관리" |
| S4 | 평가 종합 — 고객/PM/동료 평균, 가중 종합점수, 등급 (슈퍼타입⋈3서브타입) | 6~10 | `/reports/evaluations` | PD ¶4·¶5 |
| S5 | 인센티브 기초자료 — 연도별 개인 종합점수·등급·PM 추천 | 6 | `/reports/incentive` | PD ¶3 "인센티브 기초자료" |
| S6 | 투입 후보 검색 — 기간 가용 + 기술 숙련도 + 최소 등급 | 5 | `/employees?...` | 투입 업무 지원 |
| S7 | [A] 변경요청 처리 현황 — 최신 검토안·승인·동의·반영 전후 값 | 10 | `/reports/changes` | 특화 A |
| S8 | [B] 평가 결과 + 역량개선계획 + 교육 신청·수료 현황 | 9 | `/reports/training` | 특화 B |

### 대표 시나리오를 S2 로 고른 이유
- 경영진의 핵심 요구("과거 특정 시점에 어떤 직원이 어느 프로젝트에 어떤 직무로")를 그대로 구현한 질의이고, 인사고과·경력증명·감사 대응에 반복 쓰인다.
- 투입 이력은 지우지 않고 쌓이므로 **데이터가 커질수록 느려지는** 유형이라 성능 기법의 효과를 보여 주기 좋다.
- 기간 포함 조건(`start_date <= :d AND end_date >= :d`)은 단순 B-tree 로 완전히 풀리지 않아, 인덱스 종류에 따른 차이를 실험으로 보일 수 있다.

### 적용한 성능 향상 기법
`assignment` 에 **커버링 인덱스** `idx_assignment_period (end_date, start_date, project_id, emp_id, role_id, participation_rate)`.
100만 건 합성 데이터로 A(인덱스 없음) / B(복합 인덱스) / C(커버링) 비교: 최근 시점 4.0배, 중간 2.3배, 과거 1.4배 개선. 기각한 대안(요약 테이블·파티셔닝·쿼리 재작성)과 이유는 `06_성능향상기법_실험.md` 에 있다.
