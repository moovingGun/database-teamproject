# 핵심 설계 결정 보고서

> 최종 산출물. 팀이 **선택한 설계** 와 **고려했으나 채택하지 않은 대안** 의 장단점을 비교한다.

## D-1. 직원 슈퍼타입-서브타입 구현 방식

| 대안 | 설명 | 장점 | 단점 |
|---|---|---|---|
| **(채택) 슈퍼타입 + 서브타입 테이블 분리** | `employee` 공통 속성, `developer`/`staff` 고유 속성, PK 공유, 판별자 `emp_type` | 서브타입별 NULL 없음, 개발자 전용 FK(투입·평가·기술은 `developer` 참조)로 **"개발자만 투입"** 을 외래키 수준에서 보장, 가이드라인 충족 | 조회 시 조인 필요 (→ `v_employee` 뷰로 완화) |
| 단일 테이블 (nullable 컬럼) | `employee` 에 skill_grade, department 등을 모두 두고 NULL 허용 | 조인 없음, 단순 | 지원직 행의 등급 컬럼이 NULL 인 채 존재, 투입 FK 가 지원직도 허용 → 트리거로만 막아야 함 |
| 서브타입 테이블만 (슈퍼타입 없음) | `developer`, `staff` 가 각각 공통 속성을 보유 | 서브타입 단독 조회 빠름 | 사번/주민번호 유일성을 테이블 간에 보장 불가, 계정·이력 FK 대상이 둘로 갈라짐 |

## D-2. 프로젝트 평가 슈퍼타입-서브타입

| 대안 | 설명 | 장점 | 단점 |
|---|---|---|---|
| **(채택) `evaluation` + `customer_eval` / `pm_eval` / `peer_eval`** | 공통(프로젝트, 피평가자, 상태, 날짜)은 슈퍼타입, **평가자의 종류가 다른 점**(발주처 담당자 vs 개발자)과 유형별 고유 속성(토큰·의뢰자·보고일 / 인센티브 추천 / 익명 여부)을 서브타입에 둠 | 고객 평가자를 `client_contact` 로 FK 참조 가능(단일 테이블이면 evaluator 컬럼이 두 테이블을 가리켜야 함), 유형별 규칙(BR-11~14)을 서브타입 트리거로 분리 | 평가 1건 입력에 3개 테이블 INSERT (트랜잭션으로 처리) |
| 단일 `evaluation` 테이블 + `evaluator_type`, `evaluator_id` | 평가자를 다형성 컬럼으로 | 테이블 수 적음 | `evaluator_id` 에 FK 를 걸 수 없음(참조 무결성 상실), 유형별 속성이 NULL 로 섞임 |
| PM/동료 평가를 하나의 `internal_eval` 로 통합 (2단계 계층) | 평가자가 모두 개발자라는 공통점 | 테이블 1개 절약 | 계층이 깊어져 ERD 가독성 저하, PM 평가 고유 규칙(평가자=PM, 피평가자당 1건)이 다시 조건 분기로 돌아감 |

## D-3. 투입(ASSIGNMENT) 이력 모델링

| 대안 | 설명 | 장점 | 단점 |
|---|---|---|---|
| **(채택) `end_date NOT NULL` + 대리키** | 종료일 미정이면 프로젝트 종료일을 기본값으로, 조기 철수 시 UPDATE. 같은 사람이 같은 프로젝트에 기간을 달리해 여러 번 투입 가능 | 시점 질의가 `start<=d AND end>=d` 로 단순 → **범위 인덱스 적용 가능**, NULL 분기 없음 | 예정 종료일과 실제 종료일 구분이 없음(프로젝트 종료 처리 시 일괄 보정으로 해결) |
| `end_date NULL` = 진행 중 | 종료 전까지 NULL | 의미가 직관적 | 모든 시점 질의에 `(end IS NULL OR end>=d)` 가 붙어 인덱스 활용 저하, 정렬·집계에 NULL 처리 필요 |
| (project, emp) 복합 PK | 한 사람은 프로젝트당 1행 | 단순 | "설계자로 투입 → 철수 → 테스터로 재투입" 같은 실제 사례를 표현 불가 |

## D-4. 투입률(participation_rate) 도입

Problem Description 에는 없으나 "일정 기간만 투입" 과 "특급 인력의 여러 프로젝트 겸임" 을 현실적으로 표현하기 위해 도입. 대안으로 투입률 없이 "한 사람은 한 시점에 한 프로젝트" 규칙을 두는 방식은 단순하지만 아키텍트·분석자의 부분 투입을 표현하지 못해 기각. 합계 ≤100% 규칙은 겹치는 모든 구간의 시작 시점에서 합계를 검사하는 방식으로 구현하여 "A: 1~3월 60%, B: 4~6월 60%, 신규 C: 1~6월 40%" 처럼 **순차 투입은 허용** 하고 실제 초과만 거부한다.

## D-5. 비즈니스 규칙의 위치 (DB 트리거 vs 애플리케이션)

| 규칙 | 위치 | 이유 |
|---|---|---|
| 데이터 무결성 규칙 (BR-01~15: 기간, 투입률, PM 1명, 참여자 검증, 서브타입 일치, 이력) | **DB 트리거/제약** | UI 를 거치지 않는 SQL 적재·배치에도 동일하게 적용되어야 함(요구사항 2-4 의 Data Import). 시연 시 `constraint_tests.sql` 로 독립 검증 가능 |
| 워크플로우/권한 규칙 (AR-01~06: 종료 프로젝트 투입 금지, 본인만 수정, 의뢰 PM 만 보고) | **애플리케이션** | 화면 흐름·세션에 의존하고 정책 변경이 잦음 |
| 채번 (사번, 프로젝트번호) | **DB 트리거 + 카운터 테이블(행 잠금)** | 동시 가입 시 중복 방지. AUTO_INCREMENT 는 연도별 리셋·접두사 규칙을 표현할 수 없고, `MAX()+1` 은 경쟁 조건에 취약 |

## D-6. 로그인 계정 분리 (`user_account`)

`employee` 에 login_id/password 를 두는 대안 대비: 인증 정보와 인사 정보의 책임 분리, 계정 비활성화(퇴사)와 직원 이력 보존의 분리, 권한(`auth_role`)의 독립 관리가 가능. 1:1 이므로 Total:Total 1:N 제약 대상이 아니다.

## D-7. 주민등록번호 저장

요구사항상 관리 대상이므로 저장하되 (1) UNIQUE 로 중복 가입 차단, (2) 화면은 `v_employee.rrn_masked` 로 뒷자리 마스킹(본인 외), (3) 운영 시 `AES_ENCRYPT` 컬럼 암호화 + 별도 해시 컬럼으로 유일성 검사하는 방안을 권고. 과제 범위에서는 평문+마스킹을 채택(데모·채점 편의).

## D-8. 코드 테이블 vs ENUM

- 속성이 있는 코드(직무: 최소 등급 / 평가 항목: 가중치·설명 / 기술: 분류) → **테이블** (`job_role`, `eval_item`, `skill`)
- 값만 있는 짧은 고정 목록(학력, 상태, 등급, 평가 유형) → **ENUM** (조인 없이 가독성, `ENUM+0` 으로 등급 서열 비교)
- 정책 파라미터(유형별 가중치) → `eval_type_weight` 테이블로 두어 코드 수정 없이 정책 변경 가능

## D-9. 대표 시나리오 성능 향상 기법 선택

| 대안 | 평가 |
|---|---|
| **(채택) 복합 인덱스 `(end_date, start_date)`** | `end_date >= :d` 범위 스캔으로 과거 종료 투입을 배제, 두 번째 컬럼으로 ICP 필터. 생성 비용 낮고 투명함. 실험 결과 `docs/06_성능향상기법_실험.md` |
| 커버링 인덱스 (조인 키 포함) | 테이블 랜덤 I/O 제거로 추가 이득 가능하나 인덱스 크기 증가·쓰기 비용. 실험에서 함께 측정하여 비교 |
| 월별 투입 스냅샷(요약) 테이블 | 시점 질의 O(1) 이지만 투입 변경마다 재계산·동기화 필요, 임의 일자 질의 불가 → 기각 |
| 파티셔닝 (end_date 기준 RANGE) | 대용량(수천만 건) 에서 유효하나 100명 규모 조직에선 과도, MySQL 파티션 테이블의 FK 제약 미지원 → 기각 |

## D-10. 기술 스택

MySQL 8.0 (Docker): CHECK 제약 실제 적용, 트리거/프로시저, `EXPLAIN` 로 실험 가능, 팀원 환경 동일화(`docker compose up`). Flask + PyMySQL: 서버 렌더링으로 SQL 이 화면 코드에 그대로 드러나 **데모 시나리오 SQL 과 UI 가 1:1 대응** — ORM 을 쓰지 않은 이유.
