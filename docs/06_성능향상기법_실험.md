# 성능 향상 기법 및 실험 결과 — 대표 시나리오 S2 (특정 시점 투입 현황)

> 최종 산출물. 원시 측정값: `docs/06_perf_results.md` (스크립트가 자동 생성) · 재현: `.venv/bin/python scripts/perf_benchmark.py --rows 1000000`

## 1. 대상 질의와 문제

```sql
SELECT p.project_code, p.project_name, c.client_name, e.emp_no, e.emp_name, d.skill_grade, r.role_name,
       a.start_date, a.end_date, a.participation_rate
  FROM assignment a
  JOIN project p   ON p.project_id = a.project_id
  JOIN client c    ON c.client_id  = p.client_id
  JOIN employee e  ON e.emp_id     = a.emp_id
  JOIN developer d ON d.emp_id     = a.emp_id
  JOIN job_role r  ON r.role_id    = a.role_id
 WHERE a.start_date <= :as_of AND a.end_date >= :as_of;     -- "그 시점에 투입 중"
```

- 경영진의 핵심 요구("과거 특정 시점에 누가 어느 프로젝트에 어떤 직무로")이며, 인사고과·경력증명·감사 대응에 반복 사용된다.
- `assignment` 에는 PK 와 FK 인덱스(project_id, emp_id, role_id)만 있고 **날짜 컬럼에 인덱스가 없어** 조건절이 테이블 풀스캔으로 처리된다. 투입 이력은 삭제하지 않고 누적되므로 연수가 지날수록 선형으로 느려진다.
- 기간 포함 조건(`start <= d <= end`)은 B-tree 로 완벽히 해결되지 않는 "구간 검색" 이어서 어떤 인덱스가 실제로 효과가 있는지 실험으로 확인할 필요가 있었다.

## 2. 실험 설계

| 항목 | 내용 |
|---|---|
| 데이터 | 운영 스키마(`01_schema.sql`)를 그대로 복제한 `si_pms_perf` 에 합성 데이터 적재: 개발자 5,000 · 프로젝트 50,000(2006~2026) · **투입 1,000,000 건** (트리거 제외) |
| 조건 | **A** 인덱스 없음 → **B** 복합 인덱스 `(end_date, start_date)` → **C** 커버링 인덱스 `(end_date, start_date, project_id, emp_id, role_id, participation_rate)` |
| 기준일 | 최근 `2026-06-01`(대부분의 투입이 이미 종료 → 선택도 높음), 중간 `2020-06-01`, 과거 `2012-06-01`(선택도 낮음) |
| 측정 | 조건·기준일별 warm-up 1회 후 5회 실행, **중앙값(ms)** · `EXPLAIN` 의 assignment 접근 방식 기록 |
| 환경 | MySQL 8.0.x Docker(Apple Silicon), 기본 버퍼풀, PyMySQL 클라이언트에서 전체 결과 fetch 까지 측정 |

## 4. 분석

1. **최근 시점(실무에서 가장 잦은 질의)에서는 B, C 모두 약 4배 개선.** `end_date >= d` 가 대부분의 과거 투입을 배제하므로 range 스캔(약 1.9% 행 접근)이 성립한다.
2. **과거 시점으로 갈수록 B 는 무력화된다.** `end_date >= 2020-06-01` 에 전체의 절반이 해당하므로 옵티마이저는 인덱스 → 테이블 랜덤 접근보다 풀스캔이 싸다고 판단(type=ALL). 이는 구간 검색에서 단일 B-tree 가 가지는 본질적 한계다.
3. **C(커버링)는 모든 기준일에서 인덱스를 사용한다.** 조인 키와 출력 컬럼이 인덱스에 모두 있어(`Using index`) 테이블 접근 없이 인덱스 리프만 순차 스캔하면 되므로, 절반을 읽어야 하는 과거 시점에서도 풀스캔보다 빠르다(2.3×, 1.4×).
4. 결과 건수가 같은데도 과거로 갈수록 느려지는 것은 **스캔해야 하는 인덱스 구간(end_date >= d)** 이 커지기 때문이며, 결과 집합 크기와는 무관하다.

## 5. 채택과 적용

- **채택: C 커버링 인덱스 `idx_assignment_period (end_date, start_date, project_id, emp_id, role_id, participation_rate)`** — `db/init/01_schema.sql` 의 assignment 정의에 포함.
- 선택 근거: 최근 시점 성능은 B 와 동등하고, B 가 포기하는 과거 시점에서도 이득이 있다. 비용은 인덱스 1개 추가(쓰기 시 유지 비용, 100만 건 기준 약 40MB)이며 투입 데이터는 조회 대비 쓰기 빈도가 매우 낮다(월 수십 건).
- 컬럼 순서: `end_date` 를 선두에 둔 이유는 시점 질의의 기준일이 대개 "현재 또는 최근" 이어서 `end_date >= d` 의 선택도가 `start_date <= d`(대부분 참)보다 훨씬 높기 때문이다. `(start_date, end_date)` 순서는 `start_date <= d` 가 거의 모든 행에 해당하여 효과가 없다.

## 6. 고려했으나 채택하지 않은 대안

| 대안 | 기각 이유 |
|---|---|
| 월별 투입 스냅샷(요약 테이블) | 임의 일자 질의 불가, 투입 변경마다 동기화 필요(트리거 복잡도 증가), 이력 정합성 리스크 |
| `end_date` 기준 RANGE 파티셔닝 | 파티션 프루닝으로 과거 시점 질의를 더 개선할 수 있으나, MySQL 파티션 테이블은 FK 를 지원하지 않아 무결성 설계(BR-01 등)를 포기해야 함. 수천만 건 규모에서 재검토 |
| 쿼리 재작성 (`end_date BETWEEN d AND d + 최대 투입기간`) | 투입 최대 길이(예: 2년)를 가정하면 B 인덱스로도 과거 시점에서 range 가 성립하지만, 업무 규칙에 없는 가정을 질의에 심는 것이라 기각. 규칙이 생기면 적용 가능 |

## 7. 한계

- 합성 데이터의 투입 기간 분포(30일~프로젝트 종료)는 실제와 다를 수 있으며, 실제 분포에서 선택도가 달라지면 B/C 의 교차점도 달라진다.
- 단일 사용자·콜드/웜 캐시 혼합 환경의 측정이므로 절대값보다 **조건 간 상대 비교** 에 의미가 있다.
